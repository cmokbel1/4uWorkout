# CLAUDE.md

## What This App Is

**4UWorkout Trainer** — React Native app (Expo 54, RN 0.81, TypeScript strict) for discovering and saving exercises. `TrainingScreen` is the primary surface (search by body part, GIF display, similar-exercise browsing). Saved workouts live on `SavedWorkoutsScreen` (per-day log with inline set editing + calendar) and `WorkoutDetailScreen` (read-only single workout).

## Commands

```bash
expo start
expo run:ios
expo run:android
npx tsc --noEmit        # Only quality gate — no linter, no tests
```

EAS cloud builds (slow, billed):
```bash
eas build --platform android --profile production
eas build --platform ios --profile production
```

**iOS simulator gotcha** — `expo start` then `i` targets the *most recently opened* simulator, not the device it prints. A stray booted sim from a past session hijacks the target and the app never loads. Fix: `xcrun simctl shutdown all && killall Simulator`, then `i` — or press `Shift+I` in the CLI to pick the device explicitly.

## Environment

`EXPO_PUBLIC_API_BASE_URL` is required at runtime (set per build profile in `eas.json`); without it every API call throws. Don't rename the `EXPO_PUBLIC_` prefix — it's what exposes the var to JS.

Firebase config files `GoogleService-Info.plist` (iOS) and `google-services.json` (Android) must sit in `react-native-app/`, where `app.json` (`ios.googleServicesFile` / `android.googleServicesFile`) points. They come from the Firebase console, and prebuild fails without them. They identify the Firebase project but aren't secrets, and EAS only uploads files that aren't git-ignored.

## Architecture

### Screens & Navigation
React Navigation in `App.tsx`; `RootStackParamList` and `TabParamList` are the source of truth for screen names/params. A native stack holds `Start` → `Tabs` → `WorkoutDetail` (`{ workout, isDark }`); `Tabs` is a bottom tab navigator (`@react-navigation/bottom-tabs`) with **Randomize** (`Training`), **Search** (`Search`) and **Saved** (`SavedWorkouts`). Start's "Start Training" opens `Tabs` → `Training`; from outside the tabs, navigate with `navigate("Tabs", { screen: … })`. Tab screens stay mounted once visited, so switching tabs keeps their state; the tab bar is the navigation, so the tab screens have no nav cards and their cog menus only hold Dark mode. New screens: a tab in `Tabs` if it's a top-level place, otherwise on the root stack. **Naming:** the `Training` route (and `TrainingScreen`) is labelled **Randomize** everywhere a user sees it (tab, menu rows, copy), since it generates workouts from filters while Search finds specific ones; the code keeps the `Training` name. Its filter card sits under a "FIND A WORKOUT FOR ME" heading, matching Search's "SEARCH EXERCISES". The Start screen's button still says "Start Training". The app itself is "4UWorkout Trainer", so headers keep "Trainer". `SavedWorkouts` has two views (day and calendar) that are modes of the one screen, so the navigator never sees moves between them; the screen keeps its own `viewHistory`. A tab is never removed, so back between views can't be done by intercepting removal (`usePreventRemove`): instead the header shows a back button only while there's a previous view, and a `BackHandler` listener (added while focused) makes Android's back button step back too; with no previous view, Android back does the tab navigator's default (first tab). The day view keeps a Calendar card and the calendar a Today's workouts card, since those switch views within the tab. `WorkoutDetail` gets the full `Workout` param and renders it directly — no fetch, since a saved workout already carries a base64 `gifUrl`. **Dark mode** is per-screen state, not context: each screen re-reads the stored setting on focus, and tab screens start from `getLastKnownDarkMode()` (`src/storage/theme.ts`, primed by the Start screen's read) so a tab's first visit doesn't flash the light theme. The tab bar takes its colours from the focused screen (`useTabBarTheme(palette)`, called by each tab screen); icons are `TabBarIcon` (the focused one on a pill of its tint). `WorkoutDetail` still gets `isDark` as a param.

### State
No global state/context/store — each screen owns its `useState`. `TrainingScreen` holds most of it (`isBootstrapping` gates initial load; `isSearching` covers the search and the image/details request). A workout only counts as loaded when `isLoading` is false — `isSearching` **and** its GIF drawn (`WorkoutPanel`'s `onImageLoad` sets `loadedImageId`), since the base64 image takes a moment to render after the request returns. Until then the result card shows a spinner and Find shows "Loading…" with a spinner. **One trigger ends loading:** `onResultImageLoad` (the image drew, or failed) fades the card in and scrolls it to just below the top bar. The similar list is laid out as soon as the requests finish (invisible and untappable, fading in with the card), so the page is already full length when that scroll runs; the target is clamped to the content, since `scrollTo` doesn't stop at the end on iOS. New workouts go through `showWorkout`, which hides them until their image has drawn — except when the image is the one already on screen (a search re-picking the shown workout): React Native's `Image` only reloads when its source changes, so no load event would come, and loading finishes immediately instead. A search with no matches clears the old result and shows an inline "No workouts match" card (with **Clear filters** when filters are active) instead of an alert; a successful save shows as the Save button switching to "Saved" instead of an alert. The result card's loading, fade-in and scroll live in `src/hooks/useWorkoutViewer.ts` (`showWorkout`, `onResultImageLoad`, `loadListWorkout` for a search result, which only needs its image, and `loadFullWorkout` for a picked list item, which falls back to its image); the screen keeps `isSearching` and ORs it with the hook's `isImageLoading`. Saved workouts and saving live in `src/hooks/useSavedWorkouts.ts`: every storage write bumps a module-level version (`getSavedWorkoutsVersion`), and each screen using the hook re-reads storage on focus only when the version differs from the one it last loaded (always on its first focus). A counter rather than a flag, so one screen catching up doesn't hide a change from another.

### Design System (redesign in progress)
`src/theme.ts` holds the redesign's tokens: `getPalette(isDark)` (light/dark colors sampled from the mockups), `fonts` (Manrope weights) and `radius`. **Manrope** is loaded in `App.tsx` with `useFonts`; custom fonts choose their weight by family name, so set `fontFamily: fonts.bold` etc., never `fontWeight`. Icons are `Feather` from `@expo/vector-icons`.

`TrainingScreen` (and `SearchScreen`) layout: a **collapsing** top bar (app name, settings cog) and a fixed bottom bar (Find / Save workout) on its own `dock` surface with a lit top edge and an upward shadow, so it stays separate from the content scrolling under it. The bottom bar sits right above the tab bar, so it needs no safe-area padding.
- The top bar floats over the scroll view (`topBarOverlay`), and the content is padded to start below it (`paddingTop: topBarHeight + CONTENT_TOP_GAP`), so resizing the bar never changes the scroll view's layout.
- Collapse is driven by `scrollY` on the native thread (`Animated.event`, `useNativeDriver`): over `collapseDistance` (the height "Trainer" gives up, measured with `onLayout`) "Trainer" scales to `COLLAPSED_TITLE_SCALE` and the bar slides up by that height. The **app name stays visible at full size** — it slides down by the same space so it stays right above the title. Collapsed, the bar still reads "4UWORKOUT / Trainer". Only transforms are animated — never height, which the native driver can't do and which would make the content jitter.
- The cog stays visible when collapsed and opens a **menu** sheet (just Dark mode on the tab screens; `AppMenu` hides its divider when there are no navigation rows).
- `resultScrollTarget` puts the result card just below the **collapsed** bar.

Every screen now uses the new design. `StartScreen` (the first screen) reads the saved dark mode before drawing, so dark-mode users don't see a flash of the light theme, and re-reads it on focus; its logo rings' radii and colours are measured from the mockups (`StartScreen.styles.ts`).

### Shared Components
`src/components/`.
- `WorkoutPanel` — the Training screen's workout block (name, detail chips, image, description, a "Last time" note line, Instructions and Listen buttons), new design. Like the other new-design components it takes a `palette`, not `isDark`.
- `WorkoutDetailScreen` has its own layout (image card, difficulty with a 3-bar level icon, Target / Group / Gear tiles, Instructions row with a Listen button, Sets list, and the workout's note when it has one) rather than `WorkoutPanel`; both open the shared `InstructionsModal`.
- **Reading instructions aloud** — `src/hooks/useSpokenSteps.ts` (`expo-speech`) reads the steps one at a time ("Step 1. …") with a short pause between them. The **screen owns it, not the dialog**: `WorkoutPanel` and `WorkoutDetailScreen` each call the hook and pass `currentStep` / `isSpeaking` / `onToggleSpeech` to `InstructionsModal`, so the Listen button and the dialog's speaker button control one reading, the dialog highlights the step being read, and reading carries on after the dialog closes (the image stays in view). It stops when the screen loses focus (`useIsFocused`, since screens stay mounted under the ones they open), when the instruction list changes (a different workout), or on unmount. Each run has an id, so native callbacks and pause timers from a stopped run are ignored. On Android the speech engine starts lazily and a step queued before it's ready can't be cancelled, so the hook wakes the engine as soon as reading becomes possible.
- New design: `ScreenHeader` (fixed header for screens other than Training: 4UWORKOUT label and title, optional back button and cog, over a divider; used by the day view, the Calendar and Workout Detail), `InstructionsModal` (a workout's instructions as numbered steps), `AppMenu` (the cog's menu: navigation rows passed in by each screen, then the Dark mode switch; used by Training and the Calendar), `BottomSheet` (slides up over a fading scrim and back down before unmounting; used by `SelectField`, `AppMenu` and `PreviousNotes`), `SelectField` (dropdown-style field that opens a `BottomSheet` of options; `large` or `compact` with a caps label; an option can be `disabled`, with a `disabledReason` read by screen readers, e.g. "none in your difficulty range"), `RangeSlider` (two-handle slider snapping to a few levels — drag, or tap a level label for just that level, tap again for all; handles are `adjustable` for screen readers), `ThemedButton` (`primary` / `secondary`, plus `action` (filled accent) / `actionOutline` (accent outline) for Find and Save workout on Training's bottom bar, which fade rather than turn grey when disabled; optional icon), `NavCard` (navigation tile on Training, the day view and the Calendar; never highlighted, so none looks like the current screen; raised with a shadow that drops while pressed; shadows barely show on the dark background, so in dark mode the card is also a lighter fill with a lit top edge, from the `navCard*` palette tokens).
- `CalendarView` — the Saved tab's month view, new design: `ScreenHeader` (brand, title, cog menu, and a back button only when the day view is underneath), a Today's workouts `NavCard`, and a "Select a date" card (note that saved days are dotted) wrapping `react-native-calendars`, with a summary line under it for the month shown (days trained, workouts, and the current streak on the current month; the streak counts back from yesterday until something is saved today), then a Recent workouts card (the last 5 days with saved workouts, each opening that day). **Tapping a day opens the day view for it** — the same screen Training's "Today's workouts" opens — so both routes lead to one place for a day's workouts. The calendar's theme is read once by the library, so it's remounted (`key`) when dark mode changes.
- `DayView` — the Saved tab's day view ("Today's workouts"), new design: `ScreenHeader` with cog menu (and back only when the calendar is underneath), a Calendar `NavCard`, a heading with the date and workout count, and each saved workout as a card (View, Delete) that expands into a Set / Reps / Weight table with − / + steppers (reps by 1, weight by 5 lb; the number can be typed too). Stepper taps save immediately (`onChangeSet(…, save: true)`); typed values save when editing ends (`onSaveSets`). Under the table, a note row opens `NoteModal` (one field, kept out of `SaveWorkoutModal` so the keyboard has nothing else to crowd; Return saves, line breaks become spaces); until the day has its own note, the card shows `PreviousNotes` for earlier days. Collapsed cards show a small note icon. `SavedWorkoutsScreen` owns the data, storage and view history and renders `DayView` or `CalendarView`.
- **Notes** — a saved workout's `note` belongs to that day's entry (max `NOTE_MAX_LENGTH`, 140). `PreviousNotes` shows the newest note from `notesForExercise` as a small muted "Last time: …" line (12pt, 2 lines) with an "All notes (n)" link; tapping opens every note, dated, in a `BottomSheet`. Training's panel lists all of an exercise's notes; the day view only those from earlier days. Training's Save clears `note`, since a workout picked from the saved list still carries one.
- `ThemedButton` is the app's only button component (the old `ActionButton` was removed with the last old-design screen); `iconAfter` puts its icon after the label, `iconElement` takes an icon from outside Feather.

### Search & Display Flow
On mount, `TrainingScreen` fetches body parts and reads saved workouts. On search, results are Fisher-Yates shuffled into `allResults`; one becomes `currentWorkout`, the next 10 populate `searchResults` (the "Similar Workouts" list). `allResults` keeps the full set — selecting a similar workout re-shuffles and re-slices 10. Selecting a similar workout calls `getExerciseById` (server-cached), falling back to `getExerciseImageById` + local metadata. Selecting a saved workout sets `currentWorkout` directly — no fetch, `gifUrl` already stored.

### Core Data Model
`Workout` (`src/types/workout.ts`) is the single type across API responses, AsyncStorage, and UI. New API fields go here first.

### API Layer
`src/services/workoutApi.ts` — all requests go through `requestBuilder<T>()` (throws on non-2xx). Exercise images are fetched as blobs and converted to base64 data URLs via `FileReader` for offline display. `getExerciseById` hits `GET /exercises/exercise/:id`, returning full metadata with `gifUrl` already base64. `searchExercisesByBodyPart(bodyPart, filters)` returns **up to 11** random matches — filters can make it fewer, or none. `getFilterOptions` loads every body part's filter choices (`GET /exercises/filters`). `searchExercises(query)` and `getSearchSuggestions` back the Search screen. A non-2xx response throws `ApiError`, whose `status` lets a caller tell a missing route (404) or the rate limit (429) from other failures. The query string is built by hand because React Native's `URLSearchParams` doesn't implement `set()`.

**App Check** — every request (`requestBuilder` and `getExerciseImageById`) carries a Firebase App Check token in `X-Firebase-AppCheck` (`src/services/appCheck.ts`), proving to the server that it comes from a genuine install. Release builds use Play Integrity (Android) and App Attest with DeviceCheck fallback (iOS; the `appattest-environment` entitlement is set in `app.json`). `__DEV__` builds use the **debug provider**: on first launch the native SDK logs a debug token (Xcode console / `adb logcat`), and that token must be registered in the Firebase console (App Check → Apps → Manage debug tokens) or the server, in enforce mode, rejects the requests. If a token can't be obtained, the request is sent without one rather than failing. The server accepts tokenless requests while it's in monitor mode, which keeps older builds working.

### Filters
Types in `src/types/filters.ts`. `TrainingScreen` holds `filterOptions` (all body parts' choices) and `filters` (the user's choices), and sends `filters` with every search. Controls on the Training card:
- **Body part** — nothing is chosen by default (`selectedBodyPart` is `""` unless restored from `trainingSession`). Until one is picked, the field is ringed with a "1" badge and "Start here" tag, and the filters and Find are locked (dimmed, disabled); then the badge becomes a check and Find is enabled.
- **Difficulty** — `RangeSlider`; `filters.difficulties` is the contiguous range of exact levels (sent as `difficulty=intermediate,advanced`). The full range means "any" and is stored as `undefined`.
- **Target** and **Equipment** — `SelectField`s fed from `filterOptions[selectedBodyPart]`, each with an "Any" choice (`""` → `undefined`). Equipment is single-select in the UI, though `equipmentTypes` (and the server) accept several.
- **Options follow the difficulty range, without counts** — an option with no exercises *within the selected difficulty range* (`countInDifficultyRange`, summing the server's `byDifficulty`; the plain total without a difficulty filter or `byDifficulty`) is greyed out and can't be picked; the hint under the slider says why, and screen readers hear "none in your difficulty range" after its name. The counts themselves aren't shown: users read them as how many workouts Find would list, not the pool its 11 are drawn from. Availability is per option, not for Target × Equipment combinations, so a search can still come back empty (handled by the inline "No workouts match" card).
- Filter options are fetched once per session, without blocking bootstrap, and cached in `trainingSession`; if the request fails, filtering is just unavailable and the next mount retries.
- Changing body part (`onChangeBodyPart`) drops a target or equipment type the new body part doesn't offer; difficulty is kept.
- `filters` and `selectedBodyPart` are both kept in `trainingSession`, because filter choices only make sense for the body part they were picked under.
- Narrow combinations return few or no results; the empty-result alert says so when filters are active.

### Search
`SearchScreen` — keyword search, laid out like Training (collapsing top bar, result card with `WorkoutPanel`, a list under it, Save on the bottom bar) and built on the same hooks (`useWorkoutViewer`, `useSavedWorkouts`).
- **Input** — `cleanSearchInput` (`src/utils/search.ts`) drops anything but letters, digits and spaces as it's typed or pasted, so the field never shows an error; `maxLength` 40, with a counter. Search (or return) is enabled from 3 characters after trimming, with a hint under the field below that. Searches only run on Search / return, never while typing or tapping suggestions, to spare the server's rate limit. Search is also disabled while the field holds the search already on screen (ignoring case; a failed search doesn't count, so it can be retried), since Shuffle is how to repeat one, and for 3 seconds after any search or shuffle (`isSearchCoolingDown`, like Randomize's Find; Shuffle waits too). While the field holds the search on screen, the notice line says why ("Showing results for these words. Tap Shuffle for others.", or "Showing every match…" when Shuffle is hidden). An info button ("Search tips") by the "SEARCH EXERCISES" heading toggles an inline tip under the field explaining this and pointing to Shuffle (inline rather than a floating bubble, which would cover the pills); its × button or running a search closes it. The server enforces the same rules (`SEARCH_MIN_LENGTH` / `SEARCH_MAX_LENGTH` in `src/types/search.ts`).
- **Suggestions** — `SuggestionPills`, a sideways-scrolling row from `GET /exercises/search/suggestions` (loaded on mount; hidden if it fails), every value once, most common first. Tapping one adds its words to the query **without searching**, so several can be combined before tapping Search; a pill whose words are all in the query is highlighted, and tapping it takes them out. A pill that would push the query past 40 characters isn't added; the notice line says why.
- **Results** — the server returns up to 11 (`SEARCH_SAMPLE_SIZE`), closest names first and random within each rank (see the server's CLAUDE.md); the first is shown (image only, via `loadListWorkout`), the rest are listed in `SimilarWorkoutsList` as "More matches". When fewer than 11 match, the server fills the rest with exercises like the closest match, flagged `similar` on `Workout`; they're listed apart under "Similar workouts", and with a lone match the "More matches" list ("That's the only match.") is left out so the similar list takes its place. Match counts (helper text, Shuffle, the greyed-out hint) count only `matches`, not the fill. Saving strips `similar`. Picking one shows its full record and puts the previous one back in its list (no reshuffle). **Shuffle** in the list heading repeats the last search (`resultsQuery`, not the field's current text); it's hidden when fewer than 11 matched, since that's every match.
- **Session** — like Training's `trainingSession`, `src/state/searchSession.ts` keeps the field's text, the last search (`resultsQuery`, `results`) and the workout on show in memory for the session, so coming back to Search (even after a remount) shows them again; the suggestions are fetched once per session there too. Not persisted: a full reload starts Search empty.
- **Failures** — no matches clears the old result and shows an inline card with the query and **Clear search**; the field stays editable and the pills stay. A 404 (server without `/search`) replaces the results with "Search isn't available yet" and hides the pills; a 429 or network failure keeps the current results and explains on the notice line. That includes the first result's image (the search's second request, so the likeliest to hit the rate limit): `loadListWorkout` throws (`getExerciseImageById` throws `ApiError`), and the new list is only kept once the image is in. On Randomize, the same failure shows its "Search failed" alert.

### Persistence
`src/storage/savedWorkouts.ts` — JSON in AsyncStorage under `saved_workouts_v3`, a `SavedWorkoutsByDate` map keyed by local date (`YYYY-MM-DD`); each `Workout` carries per-set `setDetails` (weight/reps) and an optional client-only `note`. Earlier keys (`v1`, `v2`) are no longer read. Helpers: `readSavedWorkouts`, `writeSavedWorkouts`, `addWorkoutForToday`, `removeSavedWorkout`, `clearSavedWorkouts`, `notesForExercise` (an exercise's notes across days, newest first, optionally only before a date). Per-day dedup is enforced in the storage module: `addWorkoutForToday` leaves a workout already saved today unchanged, and `readSavedWorkouts` drops repeat copies within a day (cleaning up duplicates saved before this check existed). `TrainingScreen` also disables Save for a workout already saved today, using `useSavedWorkouts`, which loads on each mount's first focus since the version counter is module-level and survives a remount. Dark-mode preference persists separately in `src/storage/theme.ts` (`readDarkMode` / `writeDarkMode`).

### Non-Obvious Constraints
**Safe area** — always use `SafeAreaView` from `react-native-safe-area-context`, never the `react-native` built-in (a no-op on Android, so content runs under the system nav bar — especially with the edge-to-edge layout Android enforces at `targetSdkVersion` 35 and above). `SafeAreaProvider` is in `App.tsx`.

**Android SDK** — Expo SDK 54 compiles and targets API 36 by default, which Google Play requires. There is no pin in `app.json`; don't add one that lowers it.

**React Native Firebase** (`@react-native-firebase/app`, `/app-check`) has native code, so it needs a dev-client or release build — **Expo Go can't run the app**. A build made before Firebase was added must be uninstalled and rebuilt (`npx expo prebuild --clean`). Both packages are pinned to **24.1.1**: v25+ needs Xcode 26.2+, and v27 is SPM-only with dynamic frameworks. iOS uses `expo-build-properties` `useFrameworks: "static"` (Firebase needs frameworks) and `buildReactNativeFromSource: true`, which avoids clashes between static frameworks and Expo 54's precompiled React Native at the cost of slower iOS builds.

**Direct dependencies `expo-file-system` and `babel-preset-expo`** — both come with `expo`, but npm installs them under `expo/node_modules`, where Android autolinking and Babel don't look. Keep them in `package.json`. Without `expo-file-system`, Android release builds can't load any bundled font (Manrope falls back to Roboto and every icon is blank); without `babel-preset-expo`, bundling fails.

## What Not To Do
- React Navigation is the router — don't add a second (e.g. Expo Router). New screens go in `App.tsx`: a tab (`TabParamList`) for a top-level place, otherwise the root stack (`RootStackParamList`).
- No global state (Redux, Zustand, Context) — per-screen `useState` is intentional.
- Don't import `SafeAreaView` from `react-native` in new screens.
- Don't change the `saved_workouts_v3` key without a migration path (existing users lose saved workouts).
